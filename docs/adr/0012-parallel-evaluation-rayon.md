# ADR-0012: rayon による打牌候補評価・牌譜レビュー等のデータ並列化

> **ADR番号:** 0012  
> **作成日:** 2026-09-15  
> **更新日:** 2026-09-15  
> **作成者:** Antigravity AI  

---

## ステータス

`Proposed`

---

## コンテキスト（Context）

麻雀AIエンジン（`mahjong`）における打牌候補評価（`evaluate_hand_discards`）は、手牌14枚の各打牌候補（最大14通り）に対してシャンテン数計算、待ち牌探索、和了確率推計、打点計算、危険度評価を行うため、ゲーム中および局後分析において最もCPU時間を消費するホットパスです。
また、鳴き判断（`advise_call`）、着順期待値シミュレーション（`placement_ev`）、牌譜全巡レビュー（`review.rs`）も同様に独立した探索・計算タスクをループ処理しています。
これらは完全に状態が独立（Shared-nothing）しているにもかかわらず、現在はシングルスレッドの逐次ループで実行されており、近年のマルチコアCPU環境において計算性能が十分に引き出せていませんでした。

---

## 意思決定の要因（Decision Drivers）

- **レイテンシ短縮:** 対局時や牌譜分析時における打牌候補評価のレイテンシを削減し、思考時間・分析時間を大幅に短縮すること。
- **マルチコア性能の活用:** 4コア〜16コアのマルチコア環境において、ほぼ線形に近いスピードアップを実現すること。
- **コード保守性・簡潔さ:** 複雑なスレッド管理やチャネル送受信を避け、宣言的かつバグの混入しにくいイテレータ構文で並列化できること。
- **決定論的結果の維持:** スレッドのスケジューリング順序に依存せず、常に同一の評価順位・同一のタイブレーク結果が得られること。

---

## 検討した選択肢（Considered Options）

1. **Rayon によるデータ並列化 (`rayon::prelude::*`)**
2. **標準ライブラリのスコープドスレッド (`std::thread::scope`)**
3. **Tokio / 非同期タスク (`tokio::spawn`)**

---

## 決定結果（Decision Outcome）

**選択した選択肢:** **選択肢 1: Rayon によるデータ並列化**

**理由:**
- Rayon はワークスティーリング型スレッドプールを備えており、CPUバウンドなデータ並列処理（イテレータの並列化）において最小のオーバーヘッドで最適な負荷分散を実現できる。
- `into_par_iter()` や `par_iter()` への置き換えにより、既存のロジック構造を維持したまま簡潔に並列化できる。
- Python API との連携においても、GIL解放（`py.allow_threads`）下で安定して動作する実績が豊富である。

### 期待される効果（Positive Consequences）

- **線形に近いスピードアップ:** 4コアで約3〜3.5倍、8コアで約6〜7倍の処理高速化が見込まれる。
- **レビュー所要時間短縮:** 全巡目レビューやバッチ処理時のユーザー待機時間が劇的に改善される。
- **保守性向上:** スレッドプール管理やワーカー管理を手動実装する必要がなく、安全な抽象化が維持される。

### 想定されるリスク（Negative Consequences）

- `rayon` クレートの追加による依存関係とビルド時間のわずかな増加。
- 非常に小さな手牌評価（候補数が1〜2個など）でワークスティーリングの初期化オーバーヘッドが数マイクロ秒発生しうるが、1候補の評価コスト（数万〜数十万命令）に比べれば無視できるレベルである。

---

## 各選択肢の評価（Pros and Cons）

### 選択肢 1: Rayon（採用）

| 観点 | 評価 |
|------|------|
| パフォーマンス・負荷分散 | ✅ ワークスティーリングによりコア数に応じた最高効率 |
| 実装の簡潔さ | ✅ `par_iter()` に差し替えるのみ |
| 依存関係オーバーヘッド | ⚠️ `rayon = "1.10"` の追加 |

### 選択肢 2: `std::thread::scope`

| 観点 | 評価 |
|------|------|
| パフォーマンス・負荷分散 | ⚠️ スレッド起動・破棄のオーバーヘッド、あるいは自前プールの管理が必要 |
| 実装の簡潔さ | ❌ スレッド分割・ジョイン・チャネル集約などの定型コードが増加 |
| 依存関係オーバーヘッド | ✅ 外部クレート不要 |

### 選択肢 3: Tokio

| 観点 | 評価 |
|------|------|
| パフォーマンス・負荷分散 | ❌ I/Oバウンド向けのためCPUバウンド処理には適さない（スレッドプール競合） |
| 実装の簡潔さ | ❌ async/await 汚染が発生 |
| 依存関係オーバーヘッド | ❌ 巨大なランタイム依存 |
