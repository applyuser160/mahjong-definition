# ADR-0014: 大規模 match 式の算術演算・配列ルックアップへの置換最適化

## ステータス

Proposed（提案中）

## コンテキスト

麻雀エンジン内部（`TileName`、役判定 `yaku.rs`、ドラ判定 `dora.rs`）において、30〜35 分岐を持つ大規模な `match` 式が多数存在していた。
`TileName` は `#[repr(u8)]` で定義されており、値域は `0..=34` の連続した整数値である。
これに対して毎回ジャンプテーブル参照や長大な条件分岐判定が行われており、ホットパスにおける CPU 命令キャッシュ（I-Cache）の圧迫や分岐予測ミスの原因となっていた。

## 検討した選択肢

1. **選択肢 1: 現状維持（大規模 match 式）**
   - メリット: 安全で可読性が高い。
   - デメリット: 分岐数・ジャンプテーブルの肥大化によりホットパスのレイテンシと命令キャッシュ効率が低下。

2. **選択肢 2: `std::mem::transmute` と算術演算・配列ルックアップの採用（採用）**
   - メリット:
     - `TileName::from_usize`: 境界チェック (`n <= 34`) のもとで `unsafe { std::mem::transmute(n as u8) }` を用いることで、機械語レベルで無変換（0 コスト・単一比較）で高速変換可能。`const fn` にも対応。
     - `tile_type` / `category`: 数値範囲マッチングにより判定命令を大幅削減。
     - `is_number_tile`: `(idx - 1) / 9` および `(idx - 1) % 9 + 1` の算術演算で O(1) 計算。
     - `as_str` / `indicator_to_dora`: 静的配列ルックアップで即時参照。
   - デメリット:
     - `unsafe` を一部で使用するため、境界値安全性の徹底が不可欠（`n <= 34` のガードを必須化）。

3. **選択肢 3: safe な静的配列ルックアップのみの採用**
   - メリット: `unsafe` を完全に排除できる。
   - デメリット: `from_usize` において静的配列のメモリアドレス参照とロードが発生し、`transmute` に比べてレジスタ内完結が難しくなる。

## 決定事項

**選択肢 2 を採用する。**

`TileName` は `#[repr(u8)]` かつ 0（None）から 34（White）まで隙間なくバリアントが定義されているため、`n <= 34` の境界チェックを行う限り `transmute` は完全に健全（Sound）である。
また、数牌（1..=27）に対するスーツおよびランクの計算は商・余りの算術演算で正確に O(1) で行えるため、分岐予測コストをゼロにできる。

## 結果・影響

### ポジティブな影響
- `from_usize`、`tile_type`、`is_number_tile` の実行ステップ数が大幅に削減され、受入計算・役判定のスループットが向上する。
- バイナリの命令サイズとジャンプテーブルが削減され、I-Cache ヒット率が改善する。

### ネガティブな影響・リスク
- `transmute` の使用による安全性リスク。ただし `n <= 34` の明示的な境界チェックを施し、35 以上の場合は `TileName::None` を返すことで未定義動作を確実に排除する。単体テストにて 0..=255 の全域を網羅検証する。
