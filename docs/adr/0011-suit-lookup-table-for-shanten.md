# 0011: 向聴数計算におけるスーツ別ルックアップテーブル（LUT）の採用

> **ADR番号:** 0011  
> **作成日:** 2026-09-15  
> **更新日:** 2026-09-15  
> **作成者:** Syun & AI Assistant  

---

## ステータス

`Accepted`

---

## コンテキスト（Context）

麻雀エンジンにおいて、手牌の向聴数（シャンテン数）計算は打牌候補分析（`analyze_all_discards`）や打牌期待値評価（`evaluate_hand_discards`）、牌理ドリル生成、CPU思考ルーチンなど、ほぼすべての意思決定ロジックの根底に位置する超高頻度クリティカルパスです。

従来の `search_normal()` は再帰バックトラッキング（深さ優先探索）により刻子・順子・対子・搭子の組み合わせを全探索していました。しかし、数牌（萬子・筒子・索子）の各スーツは最大9種・各0〜4枚であり、各スーツ内の手牌状態数は高々 $5^9 = 1,953,125$ 通り、麻雀手牌として有効な枚数（$\le 14$ 枚）に限定するとわずか 405,350 通りしか存在しません。
これらを事前に計算してテーブル化（ルックアップテーブル / LUT）することで、再帰探索を $O(1)$ の配列アクセスに置き換えることができます。

---

## 意思決定の要因（Decision Drivers）

- **超高速化**: クリティカルパスである向聴数計算を 10〜100 倍高速化し、EV計算やシミュレーションのレスポンスを改善すること。
- **計算結果の完全一致性**: 既存の向聴数判定・受け入れ計算・役判定テストとの 100% の互換性を保つこと。
- **メモリ効率と起動速度**: メモリ使用量を 20MB 以内に収め、起動時遅延やバイナリサイズの肥大化を抑えること。
- **保守性**: スーツ独立のテーブル構造とすることで、字牌の単純計算や雀頭の選択ロジックをシンプルかつ堅牢に保つこと。

---

## 検討した選択肢（Considered Options）

- **選択肢 A: 現行の再帰的深さ優先探索（DFS）の局所的プルーニング改善**
  - メモ化テーブルの導入や枝刈り強化で再帰回数を減らす。
- **選択肢 B: スーツ別ルックアップテーブル（Base-5 エンコード LUT）+ OnceLock 遅延初期化**
  - $5^9$ のフラット配列を用意し、初回利用時に有効パターン（405,350 通り）を事前計算してキャッシュ。
- **選択肢 C: ビルド時生成（`build.rs`）による完全静的バイナリ埋め込み**
  - コンパイル時にテーブルバイナリを生成し、`include_bytes!` で静的メモリに埋め込む。

---

## 決定結果（Decision Outcome）

**選択した選択肢:** **選択肢 C（ビルド時生成 `build.rs` による静的事前生成）** を採用。

**理由:**  
- 当初検討した実行時 OnceLock 生成（選択肢 B）では、最初の向聴数計算リクエスト経路で約2秒間の同期生成が発生し、Python API や初回解析リクエストをブロッキングしてしまう課題（PRレビュー指摘）が判明したため。
- `build.rs` でコンパイル時に 1,953,125 パターンのテーブルバイナリ（約19.5MB）を出力し、`include_bytes!` でアライメントを保証してロードすることで、**実行時の初期化コストを 0.00ms（完全ゼロ）** に抑えることができる。
- これにより、冷間時・温間時を問わず初回の呼び出しからナノ秒単位の $O(1)$ 性能を発揮し、起動停止やウォームアップ漏れのリスクを根本から排除する。

### 期待される効果（Positive Consequences）

- **初回リクエストのゼロレイテンシ化**: アプリ起動直後やテスト実行時の初回向聴数計算も 0ms で即座に完了。
- **向聴数計算の劇的な高速化**: 清一色などの最悪ケースで 50µs 程度かかっていた計算が 70ns 前後に短縮（約730〜950倍の高速化）。
- **受け入れ計算・全打牌評価の連鎖的高速化**: `calculate_acceptance` や `analyze_all_discards` が桁違いに高速化。
- **堅牢性の向上**: `min(c, 4)` による飽和処理と入力検証により、同一牌5枚以上の異常入力でもパニックが発生しない。

### 想定されるリスク（Negative Consequences）

- **初回ビルド時間**: クリーンビルド時に `build.rs` の実行時間（数秒）が追加される（Cargoによる成果物キャッシュが効くため再ビルド時は影響なし）。
- **バイナリサイズ**: ライブラリバイナリが約 19.5MB 増加する（現代のデスクトップ・サーバー環境では許容範囲内）。

---

## 各選択肢の評価（Pros and Cons）

### 選択肢 A: 現行の深さ優先探索（DFS）の枝刈り改善

**概要:** 現行コードの探索順序の工夫やメモ化を行う。

| 観点 | 評価 |
|------|------|
| 高速化の度合い | ⚠️ 中立 (せいぜい 2〜3 倍程度) |
| メモリ消費 | ✅ 良い (数 KB) |
| 実装の複雑さ | ⚠️ 中立 (枝刈りロジックのバグリスク) |

- **Good:** メモリ消費が増えない。
- **Bad:** 根本的なアルゴリズムの計算量（分岐爆発）を解消できず、10〜100倍の劇的な性能向上は見込めない。

---

### 選択肢 B: スーツ別 LUT + OnceLock 遅延初期化（採択）

**概要:** $5^9$ の基数5テーブルを用意し、各スーツの面子・搭子最大数を $O(1)$ で取得。

| 観点 | 評価 |
|------|------|
| 高速化の度合い | ✅ 良い (10〜100倍) |
| メモリ消費 | ✅ 良い (約 19.5 MB) |
| 実装の保守性 | ✅ 良い (スーツ毎の独立性と字牌の明確な分離) |

- **Good:** $O(1)$ 配列アクセスにより分岐予測ミスや再帰スタックが不要。バイナリサイズが増加しない。
- **Bad:** 初回呼び出し時のみ初期化オーバーヘッドがある。

---

### 選択肢 C: ビルド時生成（`build.rs`）による静的埋め込み

**概要:** `build.rs` で生成した 15MB のバイナリを `include_bytes!` で直接埋め込む。

| 観点 | 評価 |
|------|------|
| 起動オーバーヘッド | ✅ 良い (0 ms) |
| バイナリサイズ | ❌ 悪い (ライブラリバイナリが 15MB 以上肥大化) |
| コンパイル時間 | ⚠️ 中立 (クリーンビルド時に数秒増加) |

- **Good:** 初回アクセス時の生成時間がゼロ。
- **Bad:** クレートや共有ライブラリ（cdylib）のサイズが大きくなる。
