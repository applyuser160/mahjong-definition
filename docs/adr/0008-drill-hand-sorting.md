# 何切るドリル手牌の自動理牌（ソート）方式の採用

> **ADR番号:** 0008  
> **作成日:** 2026-09-14  
> **更新日:** 2026-09-14  
> **作成者:** Syun & AI Assistant

---

## ステータス

`Accepted`

---

## コンテキスト（Context）

何切るドリル機能（CLIおよびWeb UI）において、生成された手牌（14枚）がランダムな順序で並んでいた。  
麻雀において理牌（萬子→筒子→索子→字牌、1〜9順）は手牌認識の基本であり、整列されていない手牌はプレイヤーの認知負荷を高め、牌効率の検討に集中できない問題が生じていた。  
手牌のソートをどこで・どのように行うか（フロントエンドで並べ替えるか、Rustのドリルエンジン・手牌構造体で行うか）の意思決定が必要となった。

---

## 意思決定の要因（Decision Drivers）

- **一貫性**: CLI（play_drill.rs）とWeb UI（DrillView.tsx）の両方で等しく理牌されること。
- **計算効率**: 手牌配列のインプレースソートによるオーバーヘッドの最小化（ゼロアロケーション）。
- **責務の局所化**: Hand 構造体が自身のソート能力を持ち、手牌モデルの整合性を損なわないこと。

---

## 検討した選択肢（Considered Options）

- **選択肢 A (推奨)**: Hand 構造体に sort() メソッドを導入し、DrillEngine の問題生成時に Rust 側でソートする。
- **選択肢 B**: Rust コアは変更せず、フロントエンド（React / TypeScript）および CLI スクリプト側で描画直前に独自ソートする。
- **選択肢 C**: Python API ラッパー（python_api.rs）内でのみソートする。

---

## 決定結果（Decision Outcome）

**選択した選択肢:** 選択肢 A を選択。

**理由:**  
Rust の TileName にはすでに完全な順序関係（Ord）が定義されており、Hand 構造体に sort() を備えることで、CLI、Python API、Web UI のすべてに自然かつ均一にソート済み手牌が提供される。また、他のモードや将来の拡張でも手牌の理牌が必要になった際に共通利用できる。

### 期待される効果（Positive Consequences）

- CLI・Web UI を問わず、何切るドリルで常に理牌された見やすい手牌が表示される。
- slice::sort_unstable() により、追加メモリ割り当てなし（O(1) 追加メモリ）で極めて高速に実行される。

### 想定されるリスク（Negative Consequences）

- 特になし（手牌内部のカウント counts や牌数 len は維持され、評価アルゴリズムに悪影響はない）。

---

## 各選択肢の評価（Pros and Cons）

### 選択肢 A: Hand::sort() を実装し DrillEngine で適用

| 観点 | 評価 |
|------|------|
| 一貫性 | ✅ CLI / API / Web UI すべてで統一 |
| 保守性 | ✅ コアモデルの責務として明確 |
| パフォーマンス | ✅ sort_unstable で極小オーバーヘッド |

### 選択肢 B: フロントエンド/CLIで個別ソート

| 観点 | 評価 |
|------|------|
| 一貫性 | ❌ 各クライアントで二重実装・不整合リスク |
| 保守性 | ⚠️ ロジックの散乱 |
