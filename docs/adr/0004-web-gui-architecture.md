# ADR-0004: Web/GUI インターフェースアーキテクチャの選定

> **ADR番号:** 0004  
> **作成日:** 2026-09-14  
> **更新日:** 2026-09-14  
> **作成者:** Syun & AI Assistant

---

## ステータス

`Accepted`

---

## コンテキスト（Context）

麻雀AIエンジン（コア数理・EV計算・4人対局・何切るドリル・順位期待値）のCLIプロトタイプが完成し、これを一般ユーザーが視覚的・直感的に操作して学習できるグラフィカルインターフェース（GUI）を提供するフェーズに移行した。
既存のRust資産（`mahjong_core`, `mahjong_engine`）を最大限に活かしつつ、低遅延でリッチな対局描画・リアルタイムHUD表示を実現するためのアーキテクチャ選定が必要となった。

---

## 意思決定の要因（Decision Drivers）

- **既存Rustコードの再利用性**: 複雑な麻雀ルール・EV計算・CPU思考ロジックを再実装することなく、そのまま活用できること。
- **リアルタイム性と低遅延**: 打牌操作や他家CPUの反応、リアルタイムなEV計算結果の配信がストレスなく行えること（100ms以内）。
- **開発効率とUIエコシステム**: 麻雀牌のグラフィックス描画、レスポンシブな盤面配置、HUDのチャート描画を迅速に構築できること。
- **保守性と拡張性**: 将来的なデスクトップアプリ化（Tauri等）やWebホスティング公開へスムーズに移行できる設計であること。

---

## 検討した選択肢（Considered Options）

- **選択肢 A: Rust (`axum`) バックエンド ＋ React (TypeScript / Vite) Web SPA**
- **選択肢 B: Tauri によるクロスプラットフォーム・デスクトップアプリ**
- **選択肢 C: Rustコアの WebAssembly (WASM) 化 ＋ 完全ブラウザ内完結クライアント**

---

## 決定結果（Decision Outcome）

**選択した選択肢:** **選択肢 A (Rust `axum` バックエンド ＋ React Web SPA)** を選択。

**理由:**
1. 既存のRustクレート（`mahjong_engine`等）をライブラリとしてそのまま依存に追加し、同一プロセス内で即座に呼び出せるため実装・移行コストが極めて低い。
2. WebSocketによる双方向通信を採用することで、手番進行や他家の反応を自然なイベント駆動で低遅延配信できる。
3. フロントエンドを標準的な Vite + React SPA として疎結合に開発できるため、UI/UXの改善（Tailwind CSSやSVG/Canvas活用）が容易。
4. 将来デスクトップアプリ化を望む場合でも、このReactフロントエンドをそのままTauriのフロントエンドとして転用可能。

### 期待される効果（Positive Consequences）
- ブラウザさえあればどのOSでも即座に対局・学習が可能。
- フロントエンドとバックエンドの責務がAPI/WebSocketのスキーマ（JSON）で明確に分離される。
- UIのホットリロード（Vite HMR）により、画面デザイン調整が高速に行える。

### 想定されるリスク（Negative Consequences）
- 実行時にバックエンドサーバープロセスを起動する必要がある（将来的にはワンクリック起動スクリプトやTauriバンドルで解決）。

---

## 各選択肢の評価（Pros and Cons）

### 選択肢 A: Rust (`axum`) + React SPA (採用)
**概要:** ローカルで稼働する軽量Rustサーバーと、ブラウザで動作するReact SPA。

| 観点 | 評価 |
|------|------|
| Rust資産再利用 | ✅ 既存クレートを直接利用可能 |
| 開発速度 | ✅ Web標準の豊富なエコシステムと高速HMR |
| パフォーマンス | ✅ ローカルWebSocket通信で遅延ほぼゼロ |
| 配布容易性 | ⚠️ サーバープロセス起動が必要 |

---

### 選択肢 B: Tauri デスクトップアプリ
**概要:** Rustバックエンドをネイティブプロセスとして内包し、WebViewでフロントエンドを表示。

| 観点 | 評価 |
|------|------|
| Rust資産再利用 | ✅ 直接バインディング可能 |
| 配布容易性 | ✅ exeファイル単体で配布・起動可能 |
| 環境依存 | ❌ OSごとのビルド環境（MSVC, WebView2, Linux webkit2gtk）のセットアップ負荷が高い |

---

### 選択肢 C: WebAssembly (WASM) 完結型
**概要:** Rustコードを `wasm-pack` でコンパイルしブラウザ内だけで実行。

| 観点 | 評価 |
|------|------|
| サーバーレス | ✅ 静的ファイル配信だけで動作 |
| 計算リソース | ⚠️ ブラウザのシングルスレッド制約やメモリ制約があり、深い探索で重くなる懸念 |
| 依存関係 | ⚠️ 標準ライブラリの一部機能や非同期ランタイムのWASM対応調整が必要 |
