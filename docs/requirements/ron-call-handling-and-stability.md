# 要件定義書: ロン和了処理の安定化及び通信整合性保証

## 1. 背景と課題
Web UI（`mahjong-ui`）において、CPUの捨て牌に対してユーザーが「ロン (和了)」を宣言した際、通信エラー（`POST /api/match/call 400 Bad Request`）が発生し、対局画面が停止または切断される問題が報告された。

調査の結果、以下の不整合が確認された：
1. **状態リセット漏れ**: ロン成立後（`_handle_ron`）に `self.pending_call_options` がリセットされず、UI上でロンボタンが表示され続け、二重送信時に `status != "waiting_user_call"` による例外が発生する。
2. **局終了時の不要な計算**: 局終了（`round_end`）で和了牌を含めた14枚の手牌に対してAI HUD（打牌候補評価・順位期待値計算）が実行される。
3. **通信接続の多重化**: フロントエンドのWebSocket再接続タイマーがクリーンアップされず、接続が乱立してHTTPへの不要なフォールバックを引き起こす。

## 2. 機能要件 (FR)
- **FR-01**: ロン和了、流局、局開始の各フェーズにおいて、以前の副露・和了候補情報（`pending_call_options`）および直前捨て牌情報（`last_discard`）が確実に初期化されること。
- **FR-02**: 和了牌を手牌に追加する際、すでに14枚以上ある場合は追加せず多牌を防止すること。
- **FR-03**: 局終了フェーズ（`round_end`）ではAI HUD計算を抑止し、安全かつ迅速に結果画面へ移行すること。
- **FR-04**: フロントエンドの副露プロンプト（`ActionPrompt`）は、卓ステータスが `waiting_user_call` の場合のみ副露ボタンを表示し、クリック後は即座にボタンを無効化して連打を防ぐこと。
- **FR-05**: フロントエンドのWebSocket通信管理を堅牢化し、アンマウント時のタイマークリーンアップと `readyState` に応じた正確なメッセージ送信を行うこと。

## 3. 非機能要件 (NFR)
- **NFR-01 (信頼性)**: バックエンドの全API/WebSocket endpointにおいて、不正な連続リクエストが発生してもプロセスがクラッシュせず適切なエラーまたは同一ステートを返却すること。
- **NFR-02 (テスト網羅性)**: ロン和了処理の遷移、オプションクリア、局終了ステータスの整合性をユニットテストで自動検証できること。
