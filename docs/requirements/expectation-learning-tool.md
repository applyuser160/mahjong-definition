## 1. 目的・スコープ

### 1.1 目的
麻雀の実戦対局（一人麻雀・対戦モード）を指しながら、自分の手番（ツモ直後）に**リアルタイムで各打牌の期待値（EV）ヒント**と、**「なぜその打牌が最善なのか」を説明する要因分析モデル（速度・打点・リスク）**を提示することで、プレイヤーが定量的な判断基準と麻雀理論を実践の中で深く学習できるシステムを提供する。

### 1.2 スコープ

**スコープ内:**
- 対局中の手番（ツモ番）におけるリアルタイム打牌期待値（EV）ランキングの算出・提示。
- 打牌ごとの要因分解モデルの可視化：
  - **速度（Speed）**: 向聴数、有効牌（受け入れ牌の種類と残り枚数）、和了確率。
  - **打点（Value）**: 想定される役、平均翻・符、平均和了打点、高打点変化。
  - **リスク（Safety）**: 他家の現物・筋・危険度評価（放銃リスク）。
  - **決定理由（Rationale）**: なぜその打牌を推奨するかの比較説明テキスト生成。
- 基盤計算ロジック（向聴数計算、受け入れ枚数計算、符・得点計算、ドラ計算）。
- インタラクティブ対局実行環境（対話型 CLI / ヒントHUD付きゲームループ）。
- Pythonバインディング（PyO3）を通じたデータアクセス・学習分析API。

**スコープ外（初期フェーズ）:**
- 外部オンライン麻雀プラットフォーム（天鳳、雀魂など）へのリアルタイムメモリフック・画面キャプチャ解析（初期は内部ゲームエンジン/シミュレータ環境で実施）。
- 複雑なディープラーニングモデル（強化学習ニューラルネット）の学習・推論（初期は正確な数理モデル・期待値計算式ベースで高速動作させる）。

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| **向聴数（シャンテン数）** | アガリ（和了）までに必要な最小手数の指標（0: テンパイ、1: 一向聴 ...）。 |
| **有効牌（受け入れ牌）** | 打牌後、手牌の向聴数を1つ進めることができる牌の集合およびその残り枚数。 |
| **素点期待値 (EV)** | 和了確率 × 和了時期待打点（および他家への放銃失点リスクを考慮した総合スコア）。 |
| **要因分解モデル** | 打牌の優劣を「速度（受入）」「打点（翻・役）」「安全度（守備）」の3要素に分解して比較・説明するモデル。 |
| **手番ヒントHUD** | ユーザーの手番時に打牌候補・期待値・内訳・推奨コメントをオーバーレイ/ターミナル表示する機能。 |

## 3. 全体要件

### 3.1 ユーザーニーズ
1. **実戦プレイ中のリアルタイム支援**: 何を切るか迷った際に、手番ごとに各候補牌の期待値とランキングを即座に見たい。
2. **納得感のある理由付け（なぜそうなのか）**: 単なる数値だけでなく、「枚数最大はAだが、打点上昇（タンピン三色）があるためBが最善」といった内訳・根拠を直感的に理解したい。
3. **ミスの振り返りと学習**: 自分が選んだ打牌と期待値最善打牌の差（EVロス）を把握し、牌効率・手役構想力を向上させたい。

### 3.2 前提条件・制約
- **前提条件**:
  - 既存の Rust 製麻雀エンジン（`Round`, `Hand`, `Tile`, `yaku.rs`）をコアとして拡張すること。
  - Windows 環境（PowerShell / cmd）で高速かつ安定して動作すること。
- **制約**:
  - `definition/` ディレクトリは**完全参照専用（Read-Only）**を維持すること。
  - すべてのコード・ドキュメントは `mahjong/` 配下に作成すること。
  - 思考時間制限（実戦を阻害しないよう、手番ごとの計算時間は数ミリ秒〜最大数十ミリ秒以内）。

## 4. 機能要件

### 4.1 コア計算機能 (Core Engine)

#### REQ-CORE-001: 向聴数（シャンテン数）計算
- **説明**: The system shall 一般手（面子手）、七対子手、国士無双手に対応した向聴数計算を行い、手牌の最小向聴数を高速に算出すること。
- **受入条件**:
  - [x] 和了形（-1）、テンパイ（0）、一向聴（1）〜六向聴（6）を正確に判定できること。
  - [x] 面子手と七対子手・国士無双手が競合する場合、最小の向聴数を採用すること。

#### REQ-CORE-002: 打牌候補別・有効牌（受け入れ）計算
- **説明**: The system shall 手牌（14枚）から選択可能な各打牌について、向聴数が進む有効牌一覧と、山・河・手牌から見た残り枚数を算出すること。
- **受入条件**:
  - [x] 各打牌後の受け入れ牌種（TileName一覧）および合計残り枚数を算出できること。
  - [x] テンパイ時における待ちの種類（両面、嵌張、辺張、単騎、双ポン、変則多面待ち）を判定できること。

#### REQ-CORE-003: 符計算および得点計算
- **説明**: The system shall 和了時の手牌構成・待ち形・和了方式（ツモ/ロン）から符（副底、ツモ符、門前加符、面子符、雀頭符、待ち符）を算出し、翻数と合わせて点数を算出すること。
- **受入条件**:
  - [x] 符計算（ピンフツモ20符、七対子25符、通常30符〜110符等の10符切り上げ）が正確であること。
  - [x] 親・子のツモ・ロン得点（100点単位切り上げ、満貫〜役満の点数区分）を算出できること。

#### REQ-CORE-004: ドラ・赤ドラ計算
- **説明**: The system shall 表ドラ表示牌・裏ドラ表示牌および赤ドラ（赤5m, 赤5p, 赤5s）を判定し、手牌内のドラ枚数を翻数に加算すること。

### 4.2 期待値計算＆要因分解モデル (EV & Explanatory Model)

#### REQ-EV-001: 打牌候補別期待値 (EV) 算出
- **説明**: The system shall 各打牌候補について、巡目・残り受け入れ枚数・和了時期待打点を総合した期待値スコアを算出すること。
- **計算式イメージ**:
  $$EV = P(\text{和了}) \times \text{平均和了打点} - P(\text{放銃}) \times \text{平均放銃失点}$$
- **受入条件**:
  - [x] 打牌候補すべてに対して EV スコアが算出され、降順にランキングできること。

#### REQ-EV-002: 要因分解モデル（速度・打点・リスク）の提示
- **説明**: The system shall 各打牌候補の期待値について、以下の3要素を内訳モデルとして出力すること。
  1. **速度指標 (Speed Score)**: 有効牌種数・残り枚数・和了確率
  2. **打点指標 (Value Score)**: 和了時の想定主要役・ドラ・平均得点
  3. **安全指標 (Safety Score)**: 他家警戒度・現物/筋/無筋の危険度
- **受入条件**:
  - [x] 各候補牌の「受入枚数」「想定打点」「危険度」が数値として比較可能であること。

#### REQ-EV-003: 意思決定理由（Rationale）の説明文生成
- **説明**: The system shall なぜ1位の打牌が2位以下の打牌より優れているのかを、モデルの要因差に基づき自然言語（日本語）で解説すること。
- **例**:
  - `「1m切りは受入枚数が最大（16枚）ですが、6p切り（12枚）にすることでタンヤオ・ピンフ・三色同順への変化（期待打点 +3,900点）が残るため、総合期待値で6p切りが最善です」`
- **受入条件**:
  - [x] 速度重視（受け入れ最大）と打点重視（高打点狙い）の分岐理由が明確に説明されること。

### 4.3 プレイ進行＆リアルタイムヒント表示機能 (Game & Hint HUD)

#### REQ-UI-001: インタラクティブ対局ループ
- **説明**: The system shall ユーザーが対話型コンソール（CLI）で牌をツモり、打牌を選択しながらゲームを進行できる対局ループを提供すること。
- **受入条件**:
  - [x] 配牌から局終了（流局または和了）までスムーズに対局が進行すること。
  - [x] 牌の表示が見やすい形式（ASCII / Unicode牌表記）であること。

#### REQ-UI-002: 手番時ヒントHUDの表示
- **説明**: The system shall ユーザーの手番（ツモ直後）に、打牌入力プロンプトの直前に「期待値ヒント」を自動表示すること。
- **受入条件**:
  - [x] 各打牌候補のランキング（1位〜）、期待値、受入枚数、想定打点、決定理由が表示されること。
  - [x] ユーザーがヒントの表示/非表示（オフ・オン）を切り替えられること。

### 4.4 打局振り返り＆EV損失診断機能 (Review & Diagnostics)

#### REQ-REV-001: 打牌ごとのEV損失（EV Loss）追跡
- **説明**: The system shall ユーザーが選択した打牌の期待値と、AI推奨最善打牌（EV1位）の期待値との差分（$\Delta EV = EV_{\text{best}} - EV_{\text{user}}$）を毎巡算出して記録すること。
- **受入条件**:
  - ユーザーがAI最善手を選んだ場合は EV Loss = 0.0 とする。
  - 劣後する打牌を選んだ場合、その損失点数（ロス）およびその巡目の局面情報を保持すること。

#### REQ-REV-002: 悪手・疑問手抽出と要因診断
- **説明**: The system shall EV損失が所定の閾値（軽微な疑問手: 150点以上、明確な悪手: 400点以上）を超えた打牌を自動抽出し、なぜ損失が発生したかの要因（受入枚数低下、打点見落とし、無駄な危険牌切り等）を特定すること。
- **受入条件**:
  - 悪手打牌について、最善手との要因差（受け入れ牌の差・打点差・危険度差）を比較提示できること。

#### REQ-REV-003: 局後学習レポート（Match Review Summary）の生成
- **説明**: The system shall 対局終了時（和了または流局）に、その局の総EV損失、打牌精度（AI一致率）、および悪手ワーストランキング（巡目・選んだ牌・推奨牌・損失点・理由）をまとめた学習レポートを出力すること。
- **受入条件**:
  - ターミナル上で見やすい表形式で学習レポートが表示されること。

---

### 4.5 4人対局CPU学習モード (4-Player CPU Match Mode)

#### REQ-CPU-001: 4人麻雀対局ループ
- **説明**: The system shall 自家（プレイヤー）と3名のCPU（AIエージェント）による4人対局（東風戦/1局単位）を進行できる対局ループを提供すること。
- **受入条件**:
  - 他家のツモ・打牌・リーチ・和了・放銃が正しく処理されること。

#### REQ-CPU-002: 他家リーチ・仕掛け時の危険度・押し引き評価連動
- **説明**: The system shall 他家がリーチや副露（鳴き）を行っている局面において、他家の捨て牌から現物・筋を判定し、各打牌の危険度（Safety Metric）をリアルタイムに計算してEVおよび押し引きヒントに反映すること。
- **受入条件**:
  - 他家の現物は危険度 0.0、筋牌は低危険度、無筋・生牌は高危険度として評価されること。
  - 自分の向聴数や打点と他家リスクを比較し、「押し」「引き（オリ）」の意思決定理由が提示されること。

### 4.6 何切るドリル・クイズモード (What-to-Discard Drill Mode)

#### REQ-DRILL-001: 何切る問題の自動生成
- **説明**: The system shall 14枚の手牌（ツモ直後状態）から、指定された向聴数条件（テンパイ、一向聴、二向聴など）に合致する「何切る問題」を自動生成すること。
- **受入条件**:
  - ランダムな有効牌姿を生成し、打牌候補が複数存在する局面を出題できること。
  - ドラ表示牌、巡目、自風・場風のコンテキストが付与されること。

#### REQ-DRILL-002: 即時採点・EV損失・要因解説のフィードバック
- **説明**: The system shall ユーザーが選択した打牌に対して、AI推奨最善手との正誤判定（正解/不正解）、EV損失（$\Delta EV$）、受入枚数差、想定打点差、および「なぜ最善なのか」の自然言語解説を即座に表示すること。
- **受入条件**:
  - 解答直後に候補ランキング上位と解説が表示され、1問ごとに復習・学習できること。

#### REQ-DRILL-003: ドリルセッション成績集計・ランク評価
- **説明**: The system shall 連続解答セッション（例: 5問〜10問単位）の終了時に、正答率、平均EV損失、総合ランク評価（S〜C）を集計出力すること。

---

### 4.7 副露（鳴き：チー・ポン・カン）判断アドバイザー (Call & Meld Advisor)

#### REQ-CALL-001: 鳴き候補の抽出
- **説明**: The system shall 他家の捨て牌に対して、手牌から可能な鳴き（ポン、チー、カン）の組み合わせをすべて検出すること。
- **受入条件**:
  - 上家からの打牌に対してチー候補（連続する2枚）、他家からの打牌に対してポン候補（対子2枚）を正しく抽出できること。

#### REQ-CALL-002: 鳴き後手牌と門前維持の定量比較・推奨度判定
- **説明**: The system shall 鳴いた場合（副露成立後）の向聴数・受け入れ・喰い下がり想定打点と、スルーして門前を維持した場合の期待値を定量比較し、推奨度（積極推奨 / 鳴き微有利 / スルー推奨 / 鳴き厳禁）を提示すること。
- **受入条件**:
  - 役なしの無駄鳴きを防止し、役牌バックやタンヤオ鳴き、ドラ利用の期待値向上を判定できること。

## 5. 非機能要件

| 区分 | 要件内容 |
| :--- | :--- |
| **性能・応答性** | 1打牌あたりの期待値計算およびヒント生成は **50ms 以内** に完了し、プレイのテンポを損なわないこと。 |
| **保守性・テスト** | すべての計算モジュール（向聴数、受け入れ、符計算、EV、振り返り診断、ドリル、鳴き判断）に対して Rust 単体テストを整備し、テストカバレッジを維持すること。 |
| **ポータビリティ** | Windows PowerShell / cmd 環境で追加依存なしでネイティブ動作すること。 |
