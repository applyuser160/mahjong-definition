## 1. 目的・スコープ

### 1.1 目的

麻雀AIエンジン（`mahjong`）における打牌候補評価（`expectation.rs`）、有効牌計算（`acceptance.rs`）、手牌管理（`hand.rs`）、および副露判断（`call_advisor.rs`）は、毎打牌・毎ツモ時に膨大な回数呼び出される超高頻度ホットパスです。

これまで、各処理内部で固定上限サイズ（最大34牌種、最大4副露、最大10役名、相手3人）のコレクションに対して標準ライブラリの動的配列 `Vec` が用いられており、以下のような性能課題が生じていました：
1. **頻繁なアロケータ呼び出し**: スジ判定や有効牌集計、手牌クローンの度にヒープ確保と解放が発生。
2. **キャッシュ局所性の低下**: ヒープポインタへの間接参照によりCPUキャッシュミスを誘発。
3. **線形探索オーバーヘッド**: スジ判定等で `Vec::contains()` による線形スキャンが行われていた。

本改修の目的は、固定長で上限が確定しているコレクションをスタック完結型データ構造 `ArrayVec`（`arrayvec` クレート）に置き換え、さらにリーチ河のスジ判定等を `u16` ビットマスクに置換することで、ホットパスでのヒープ割り当てを完全に排除し、打牌判断およびシミュレーションの大幅な高速化を達成することです。

### 1.2 スコープ

**スコープ内:**
- `Cargo.toml` への `arrayvec = "0.7"` の依存関係追加
- `evaluate_tile_safety()` におけるリーチ者の同色数字収集の `u16` ビットマスク化
- `evaluate_tile_safety()` における `riichi_opponents` の動的 `Vec` 割り当て排除（ループ内インラインフィルタ）
- `AcceptanceResult.waits` の `ArrayVec<WaitTile, 34>` 化
- `SpeedMetric.accepted_tiles` の `ArrayVec<TileName, 34>` 化
- `ValueMetric.primary_yaku` の `ArrayVec<&'static str, 10>` 化
- `Hand.open_melds` の `ArrayVec<Meld, 4>` 化による `Hand` のスタック完結化
- `python_api.rs`、`explanation.rs`、`review.rs` 等の型シグネチャ整合対応

**スコープ外:**
- 麻雀のルール・役判定結果の変更
- 評価アルゴリズム（EV計算式）のロジック変更
- 公開 Python API のシグネチャ変更（Python側からは透過的に同一の振る舞い）

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| `ArrayVec<T, CAP>` | ヒープ確保を行わず、インライン（スタック）上に固定容量 `CAP` まで要素を格納可能な可変長配列コンテナ。 |
| `WaitTile` | 有効牌（待ち牌）の牌種と残り枚数を表す構造体。最大34種類。 |
| `AcceptanceResult` | 現在の手牌に対するシャンテン数と有効牌リスト（`waits`）を保持する集計構造体。 |
| `Hand` | プレイヤーの手牌（門前面子・副露・牌種カウント）を管理する構造体。 |
| `Meld` | 副露（チー・ポン・大明槓・加槓・暗槓）。1手牌あたり最大4組。 |

## 3. 機能要件

### 3.1 ビットマスク化要件

#### REQ-001: リーチ河ランク収集のビットマスク化
**説明:**  
`evaluate_tile_safety()` において、リーチ者の河に含まれる同色数牌のランク（1〜9）を `u16` ビットマスク（`1 << rank`）で記録し、スジ判定をビット演算（`&`、`|`）で O(1) 判定すること。

**受入条件:**
- [ ] ヒープ割り当て（`Vec::new()`）が一切発生しないこと。
- [ ] ビット演算によるスジ・片スジ判定の結果が既存実装と完全に一致すること。

#### REQ-002: リーチ対局者収集のヒープ排除
**説明:**  
`evaluate_tile_safety()` において、リーチ者リストを `Vec<usize>` に `collect()` せず、直接 0..4 のインデックス走査で判定すること。

**受入条件:**
- [ ] `Vec<usize>` のヒープ割り当てが排除されること。
- [ ] 自家を除外したリーチ者の判定ロジックが既存と同一であること。

### 3.2 ArrayVec によるスタック完結化要件

#### REQ-003: AcceptanceResult.waits の ArrayVec 化
**説明:**  
`AcceptanceResult.waits` の型を `Vec<WaitTile>` から `ArrayVec<WaitTile, 34>` に変更すること。

**受入条件:**
- [ ] 最大34要素がスタック上に確保され、ヒープ割り当てが発生しないこと。
- [ ] `calculate_acceptance()` が正常に動作し、テストがすべてパスすること。

#### REQ-004: Hand.open_melds の ArrayVec 化
**説明:**  
`Hand.open_melds` の型を `Vec<Meld>` から `ArrayVec<Meld, 4>` に変更すること。

**受入条件:**
- [ ] 副露数が最大4組までスタック上で管理され、`Hand` 構造体のクローンがポインタ追従なしの memcpy 相当になること。
- [ ] 副露操作（チー、ポン、カン、加槓）が正しく動作すること。
- [ ] `call_advisor.rs` での `hand.clone()` がヒープアロケーションフリーになること。

#### REQ-005: 指標構造体（SpeedMetric / ValueMetric）の ArrayVec 化
**説明:**  
`SpeedMetric.accepted_tiles` を `ArrayVec<TileName, 34>` に、`ValueMetric.primary_yaku` を `ArrayVec<&'static str, 10>` に変更すること。

**受入条件:**
- [ ] 打牌候補ごとの評価ループ内でのヒープ割り当てが排除されること。
- [ ] 容量上限（34および10）を超過した場合にパニックせず安全に扱われること。

## 4. 非機能要件

### 4.1 性能要件
- ホットパス（`calculate_acceptance`, `evaluate_tile_safety`, `estimate_hand_value`）におけるメモリアロケータ呼び出し件数をゼロにする。
- 既存の打牌判断結果・評価値に影響を与えないこと（決定論的互換性の維持）。

### 4.2 保守性・互換性
- Python バインディング（`python_api.rs`）において、既存の Python 向け API シグネチャおよび返却型（リスト、辞書等）の互換性を 100% 維持する。
